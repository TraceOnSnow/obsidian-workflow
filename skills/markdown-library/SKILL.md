# Markdown 内容库

使用已安装的 `markdown-library` CLI，或本技能目录中的 `scripts/library.py` 包装入口。需要 Python 3.11+ 和项目依赖。先查看 `--help`，为每次命令显式指定 `--vault`；不要从文档示例猜测用户的实际库路径。只在用户明确新建库时运行 `init`。

## 读取与修改

1. 使用 `list --query 关键词` 查找候选，再按稳定 ID `get ID` 读取完整当前稿。
2. 根据用户当前请求确定范围，保留稳定 ID、未知属性、代码、日期精度和必要细节。私人经历、用户观点、引用及 AI 补充应区分来源，不补造经历或验证结果。
3. 使用 `replace ID FILE --expected-hash SHA` 写入完整逻辑 Markdown；SHA 来自刚读取的当前稿。出现并发变化时重新读取并比较差异，不用旧内容强制覆盖。
4. 回读实际保存结果，再报告改动。Agent 自行获取守卫值，不要求用户手工管理哈希。

已有普通笔记可用 `register PATH` 预览原位纳管，明确执行时携带原文件哈希与 `--apply`。模板、工具配置和导航不作为普通笔记批量纳管。新建笔记用 `create`，上游材料导入用 `import` 及稳定 `--source-id`；重复导入应保留后续用户编辑。

## 作品与独立文章

Work 使用稳定 ID 连接作品总表、私人感想和网站资料。日常字段由总表维护；有实质正文才创建感想文件。先用 `get` 读取完整逻辑 Work，再通过 `replace` 保存，让程序拆分表格字段和正文，不把完整逻辑稿直接覆盖到物理感想文件。

评分采用 0–100，0 有效，空值表示未知；输入 5 就是 5 分，不推测旧量表或批量乘十。保留多段体验、行 ID、手填日期和用户布局，不用最后运行日期推断通关。缺省网站字段不表示清空。

私人 note／Work 与 Post 独立保存，不原位改 `kind`。准备发表稿时沿用已存在的来源关系和 Post 身份，包括归档稿，并保留双向入口。Work 正文复制为关联 Post 可用 `prepare-work-review ID --expected-hash SHA` 预览；按返回的 token 执行，已有 Post 还需要其当前哈希。覆盖独立编辑前先核对本次授权范围。此命令只保存草稿，不发表。

## 发表、同步与删除

普通保存不表示发表。只有明确要求公开时，才用当前 SHA 选择 `publish` 快照，并按已配置目标执行同步。Work 卡片可公开字段与私人正文分开；Post 正文单独选版。匿名化、时间和公开范围以当前用户要求为准，不推断授权。

`sync` 默认读取和预览，`--apply` 才执行；显式提供目标 URL 与命名 API-key 环境变量。双端修改比较共同基线，冲突使用 `sync-review`／`sync-resolve`，不手改隐藏状态选边。写入超时先对账，不重复新建；只有实际远端回读和需要的前台检查通过，才报告上线。

确认删除使用可恢复生命周期；扫描缺失、改名、离线或远端 404 不构成删除授权。恢复不会自动重新公开。永久删除须有明确具体范围，不能顺带清理来源、历史或备份。

`.markdown-library/` 保存来源、历史、映射与发布状态，由程序管理。不要直接编辑这些文件消除冲突，不打印凭据、认证状态或私人原稿。库端工具记录不能替代数据库、媒体和完整库备份。服务启动、插件安装、批量旧库整理和付费模型调用需要属于用户当前授权范围。

本地部署若在同目录提供 `LOCAL.md`，请先读取其中的库位置、用户偏好和运行约定；该文件由使用者维护并通过Git忽略，不随仓库共享。当前用户请求优先，约定本身不授予额外操作权限。
